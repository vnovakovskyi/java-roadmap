# Recursion

> [!info] Topic
> **Area:** Core Java · **Module:** 2 · **Priority:** good · **Est:** 2h
> **Why this matters:** Recursion — a method calling itself — is how you solve problems that contain
> smaller copies of themselves: folders inside folders, trees, divide-and-conquer. It's also a
> classic interview topic, and it trains you to think in terms of a base case and a step.

## Learning Objectives
- Write a recursive method with a base case and a recursive step.
- Trace a recursive call stack by hand and in the debugger.
- Know when a loop is the better choice.

## Concepts
- [ ] Every recursive method needs a **base case** (stop) and a **recursive step** that moves toward
      it.
- [ ] Each call gets its own frame on the **call stack**; frames unwind as calls return.
- [ ] No base case (or a step that never reaches it) → `StackOverflowError`.
- [ ] Classics: factorial, sum of digits, reversing a string, binary search, walking a folder tree.
- [ ] Naive recursive Fibonacci recomputes the same values over and over — exponential time.
      Remember results (memoization) or use a loop.
- [ ] Anything recursive can be written with a loop. Prefer loops for simple counting; recursion
      shines on tree-shaped problems.

## Practice
**Goal:** Think recursively and see the stack.
**Steps:**
- [ ] Write `factorial(n)` recursively and with a loop; compare.
- [ ] Write `sumDigits(1234)` → `10` and a recursive `isPalindrome(String)`.
- [ ] Step through `factorial(4)` in the debugger and watch the frames stack up and unwind.
- [ ] Remove the base case and observe the `StackOverflowError`.

## Self-check
Answer out loud or on paper first, then expand to compare.

> [!question]- What two parts does every recursive method need?
> A base case that returns without recursing, and a recursive step that calls itself on a smaller
> problem, moving toward the base case.

> [!question]- What causes a `StackOverflowError`?
> Too many nested calls — usually a missing or unreachable base case — so the call stack runs out of
> space.

> [!question]- Why is naive recursive `fib(45)` so slow?
> It solves the same subproblems again and again; the number of calls grows exponentially.
> Memoization or a simple loop makes it linear.

> [!question]- When is a loop a better choice than recursion?
> For straightforward repetition (counting, summing a list): a loop is simpler, faster, and can't
> overflow the stack.
