# Building the REST API End-to-End

> [!info] Topic
> **Area:** Project · **Module:** 10 · **Priority:** must · **Est:** 6h
> **Why this matters:** This is the heart of the capstone: turning your design into a working API
> with controllers, services, DTOs, validation, and errors. Finishing it is the strongest signal
> you're job-ready.

## Learning Objectives
- Implement full CRUD across the controller and service layers.
- Use DTOs and validation.
- Wire the layers together cleanly.

## Learn
- [ ] Revisit [[M9.03 - Spring - Controllers and REST Endpoints]],
      [[M9.04 - Spring - Services and Dependency Injection]], and
      [[M9.06 - Spring - Validation and Error Handling]].

## Concepts
- [ ] Build each layer for your design: `@RestController` → `@Service` → repository (an in-memory
      one for now; the database comes next).
- [ ] Map DTOs/records to and from your domain; validate inputs with `@Valid`.
- [ ] Return correct status codes (201 create, 200 read/update, 204 delete, 400 invalid, 404
      missing, 409 conflict).
- [ ] Keep controllers thin; put logic in services.
- [ ] Add global error handling with `ProblemDetail` so failures look the same everywhere.
- [ ] Work in small branches and PRs with CI from the first commit
      ([[M6.08 - Tooling - Continuous Integration with GitHub Actions]]).

## Practice
**Goal:** A working API (in-memory persistence is fine for this step).
**Steps:**
- [ ] Generate the project on start.spring.io and set up CI.
- [ ] Implement all CRUD endpoints for your primary resource, then the related one.
- [ ] Add request/response DTOs, validation, and the global error handler.
- [ ] Exercise every endpoint with curl/HTTPie, including error cases; save the commands in the
      README.

## Self-check
Answer out loud or on paper first, then expand to compare.

> [!question]- What belongs in the controller, and what in the service?
> Controller: HTTP concerns — mapping, validation trigger, status codes, DTO conversion. Service:
> business rules and transactions. If logic would be useful without HTTP, it belongs in the service.

> [!question]- Which status codes does your API return for create, delete, invalid input, and a missing resource?
> 201 Created (with Location), 204 No Content, 400 Bad Request with field errors, and 404 Not Found.

> [!question]- Why put the in-memory storage behind the same interface the database version will use?
> So switching to the database in the next step touches only the storage implementation, not the
> controllers or services.

## Definition of Done
- [ ] All CRUD endpoints work with correct status codes.
- [ ] Inputs are validated and errors are consistent.
- [ ] Logic lives in services, and CI checks every change.
- [ ] I can answer the Self-check questions without peeking.
