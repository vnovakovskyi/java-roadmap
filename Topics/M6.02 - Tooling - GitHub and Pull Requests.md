# GitHub and Pull Requests

> [!info] Topic
> **Area:** Tooling · **Module:** 6 · **Priority:** must · **Est:** 3h
> **Why this matters:** GitHub is where your code lives publicly and where teams collaborate. A
> clean profile with real projects is part of your résumé; the pull-request flow is how professional
> teams ship.

## Learning Objectives
- Sync local and remote repositories.
- Use the branch → pull request → review → merge workflow (and forks for other people's projects).
- Write good commit messages and PR descriptions.

## Learn
- [ ] Read:
      [GitHub Docs — About pull requests](https://docs.github.com/en/pull-requests/reference/pull-requests).
- [ ] Read: [How to Write a Git Commit Message](https://cbea.ms/git-commit/).
- [ ] Set up:
      [Connecting to GitHub with SSH](https://docs.github.com/en/authentication/connecting-to-github-with-ssh)
      (or keep using the GitHub CLI / IDE login).

## Concepts
- [ ] **Remote** (`origin`): `git fetch` downloads, `git pull` = fetch + merge, `git push` uploads.
- [ ] Typical flow: branch → commit → push → open a **pull request** → review → CI passes → merge →
      delete the branch → pull `main`.
- [ ] A good PR is small and focused, with a description of *what* and *why* plus how to verify it.
      Review your own diff before asking anyone else.
- [ ] Merge strategies: merge commit, **squash** (one commit per PR — common), rebase.
- [ ] **Fork** = your own copy of someone else's repository, used to propose changes when you can't
      push to the original.
- [ ] README, license, and a tidy history make a repository look professional.

## Practice
**Goal:** Ship changes via pull requests — including to someone else's project.
**Steps:**
- [ ] Push your `java-practice` repository (if you haven't); clone it into a second folder and sync
      a change between them.
- [ ] Make a change on a branch, push it, open a PR against `main`, review your own diff, and merge
      it.
- [ ] Contribute to this roadmap: fork it, fix a typo or an outdated link, and open a PR.

## Self-check
Answer out loud or on paper first, then expand to compare.

> [!question]- `git fetch` vs `git pull`?
> `fetch` downloads new commits without touching your current branch; `pull` fetches and then merges
> (or rebases) them into your branch.

> [!question]- What makes a good pull request?
> Small and focused, a clear title and description (what, why, how to verify), passing checks, and a
> diff the author has already reviewed.

> [!question]- When do you fork instead of branching?
> When you don't have push access to the repository — e.g. contributing to open source. You push to
> your fork and open a PR to the original.

## Definition of Done
- [ ] I can push, pull, and clone, and keep two copies in sync.
- [ ] I can open, review, and merge a pull request.
- [ ] I opened a PR to a repository I don't own.
- [ ] I can answer the Self-check questions without peeking.
