# Design Patterns (the Essential Few)

> [!info] Topic
> **Area:** OOP · **Module:** 3 · **Priority:** good · **Est:** 4h
> **Why this matters:** Design patterns are named, proven solutions to recurring design problems.
> Knowing a handful lets you recognize them in the JDK and in Spring, discuss designs with a shared
> vocabulary, and answer one of the most common junior interview questions. Learn the few you'll
> actually meet — not all 23 from the classic "Gang of Four" book.

## Learning Objectives
- Explain what a design pattern is and the three classic categories.
- Implement Builder, Strategy, Observer, and Decorator in Java.
- Recognize patterns in the JDK and Spring — and know when not to use one.

## Learn
- [ ] Read:
      [Refactoring.Guru — What's a design pattern?](https://refactoring.guru/design-patterns/what-is-pattern),
      then the patterns below from its [catalog](https://refactoring.guru/design-patterns/catalog)
      (each has a Java example).
- [ ] Reference: [Java Design Patterns](https://java-design-patterns.com/) — a large open-source
      collection of Java implementations.
- [ ] Optional: *Head First Design Patterns, 2nd ed.*, and *Effective Java* items 1–3 (static
      factories, Builder, Singleton).

## Concepts
- [ ] A pattern is a reusable *idea* — a problem, the shape of a solution, and its trade-offs — not
      code to paste. Classic categories: **creational**, **structural**, **behavioral**.
- [ ] Creational: **Builder** — readable construction of objects with many (optional) parameters
      (`HttpRequest.newBuilder()…build()`); **Factory Method / static factory** — a method that
      decides what to create (`List.of`, `Integer.valueOf`); **Singleton** — exactly one instance
      (in Java an `enum`, or let Spring manage it).
- [ ] Structural: **Adapter** — makes an incompatible interface fit (`Arrays.asList`,
      `InputStreamReader`); **Decorator** — adds behavior by wrapping
      (`new BufferedReader(new FileReader(...))`, `Collections.unmodifiableList`); **Proxy** — a
      stand-in that adds behavior around calls (Spring's `@Transactional` works through one);
      **Facade** — a simple API over a complex subsystem.
- [ ] Behavioral: **Strategy** — interchangeable algorithms behind an interface (`Comparator` is
      one); **Observer** — subscribers react to events (Spring application events); **Template
      Method** — a fixed skeleton with overridable steps; **Command** — a request as an object;
      **Iterator**.
- [ ] In Module 5, lambdas turn Strategy and Command into one-liners — a functional interface *is*
      the strategy.
- [ ] Every pattern adds indirection. Use one when its problem is actually present (YAGNI); a
      pattern applied for its own sake is cargo-cult programming.

## Practice
**Goal:** Implement the patterns you'll meet most and find them in code you already use.
**Steps:**
- [ ] Give a `Pizza` class with several optional toppings a Builder; compare it with a constructor
      taking eight parameters.
- [ ] Implement a pricing Strategy (`DiscountStrategy` with two implementations) and switch between
      them at runtime.
- [ ] Write an Observer: an `OrderService` that notifies listeners (e.g. email and audit log) when
      an order is placed.
- [ ] Wrap a `Notifier` in a `LoggingNotifier` decorator without changing the original class.
- [ ] Find three patterns in JDK classes you've already used.

## Self-check
Answer out loud or on paper first, then expand to compare.

> [!question]- What is a design pattern — and what isn't it?
> A named, reusable solution idea for a recurring design problem, with known trade-offs. It isn't a
> library or a snippet to paste; you adapt the idea to your code.

> [!question]- When does a Builder pay off?
> When an object has many parameters, especially optional ones: construction becomes readable
> (`new Pizza.Builder().size(LARGE).cheese().build()`), and the result can still be immutable.

> [!question]- Strategy vs Template Method?
> Strategy swaps a whole algorithm by composition — you pass in a different object or lambda.
> Template Method fixes the algorithm's skeleton in a base class and lets subclasses override
> individual steps (inheritance).

> [!question]- Why is a classic hand-written Singleton often considered an anti-pattern?
> It's global state: dependencies are hidden, it's hard to replace in tests, and mutable singletons
> cause concurrency bugs. Prefer dependency injection — Spring beans are singletons managed by the
> container — or an `enum` when you truly need one instance.

> [!question]- Name three design patterns Spring uses.
> Proxy (`@Transactional`, method security), Singleton (the default bean scope), Template Method
> (`JdbcTemplate`), Observer (application events), Factory (`BeanFactory`).
