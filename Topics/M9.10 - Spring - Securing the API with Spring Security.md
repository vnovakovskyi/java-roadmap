# Securing the API with Spring Security

> [!info] Topic
> **Area:** Spring · **Module:** 9 · **Priority:** must · **Est:** 5h
> **Why this matters:** A real API can't be wide open. A junior is expected to understand
> authentication vs authorization, lock down endpoints, store passwords safely, and know where
> tokens like JWT fit. This is the security baseline for the capstone.

## Learning Objectives
- Explain authentication vs authorization.
- Add Spring Security and protect endpoints by path and role.
- Understand password hashing, CSRF, and token (JWT) auth at an overview level.

## Concepts
- [ ] **Authentication** = who you are; **authorization** = what you're allowed to do.
      Missing/invalid credentials → 401; authenticated but not allowed → 403.
- [ ] Adding `spring-boot-starter-security` secures everything by default — then you configure
      what's public vs protected in a `SecurityFilterChain` bean. *(Spring Security 7)* Only the
      lambda style shown below works — older `.and()` chains were removed.
- [ ] Start simple: HTTP Basic with users and roles; restrict by path, HTTP method, and role;
      `@PreAuthorize` with `@EnableMethodSecurity` for method-level rules.
- [ ] Never store plaintext passwords — hash them with a slow, salted algorithm (BCrypt via
      `PasswordEncoder`).
- [ ] **CSRF** protection matters when browsers send credentials automatically (session cookies). A
      stateless API called with explicit credentials or tokens usually disables it.
- [ ] **JWT / token auth**: the client sends a signed token on every request and the server verifies
      it (stateless). In practice you let an identity provider (Keycloak, Auth0, Okta…) issue tokens
      and configure Spring as an **OAuth2 Resource Server** — don't hand-roll JWT code.
- [ ] Test security with `@WithMockUser` (from `spring-security-test`). Keep secrets out of code
      ([[M9.07 - Spring - Configuration and Profiles]]).

```java
@Bean
SecurityFilterChain api(HttpSecurity http) throws Exception {
    return http
        .authorizeHttpRequests(auth -> auth
            .requestMatchers(HttpMethod.GET, "/api/books/**").permitAll()
            .requestMatchers("/api/admin/**").hasRole("ADMIN")
            .anyRequest().authenticated())
        .httpBasic(Customizer.withDefaults())
        .csrf(csrf -> csrf.disable()) // OK only for a stateless API without browser sessions
        .build();
}
```

## Practice
**Goal:** Lock down the API.
**Steps:**
- [ ] Add Spring Security; confirm `curl` now gets 401 on every endpoint (a browser is redirected to
      a login page).
- [ ] Configure a `SecurityFilterChain`: public `GET` of books, authenticated writes, an admin-only
      area.
- [ ] Store users with BCrypt-hashed passwords (in memory for now) and test: anonymous → 401, user
      on admin endpoint → 403, admin → 200.
- [ ] Write a `@WebMvcTest` that checks the rules with `@WithMockUser`.

## Self-check
Answer out loud or on paper first, then expand to compare.

> [!question]- Authentication vs authorization — and their HTTP status codes?
> Authentication proves identity (failure → 401); authorization decides permissions for an
> identified user (failure → 403).

> [!question]- Why BCrypt instead of SHA-256 for passwords?
> BCrypt is deliberately slow and salted, so stolen hashes are expensive to brute-force. Fast hashes
> like SHA-256 can be tried billions of times per second.

> [!question]- When does an API need CSRF protection?
> When the browser sends credentials automatically — e.g. session cookies — because another site
> could then trigger requests on the user's behalf. Token- or Basic-auth APIs without cookies
> usually don't.

> [!question]- How is a JWT checked, and why not write that code yourself?
> The server verifies the token's signature with the issuer's key and checks claims like expiry.
> Security code is easy to get subtly wrong, so use Spring's OAuth2 Resource Server with a real
> identity provider.
