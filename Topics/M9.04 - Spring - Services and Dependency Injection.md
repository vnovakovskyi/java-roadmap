# Services and Dependency Injection

> [!info] Topic
> **Area:** Spring · **Module:** 9 · **Priority:** must · **Est:** 4h
> **Why this matters:** Dependency injection is the heart of Spring. It's how the framework wires
> your objects together — and the reason your code stays decoupled and testable (Module 7 pays off
> here). Transactions live at this layer too.

## Learning Objectives
- Explain inversion of control and dependency injection.
- Use `@Service`, `@Component`, `@Repository` and constructor injection.
- Structure an app into controller → service → repository layers and use `@Transactional`.

## Learn
- [ ] Read:
      [Spring Framework — Introduction to the IoC Container](https://docs.spring.io/spring-framework/reference/core/beans/introduction.html)
      and
      [Dependency Injection](https://docs.spring.io/spring-framework/reference/core/beans/dependencies/factory-collaborators.html).
- [ ] Read:
      [Declarative Transaction Management](https://docs.spring.io/spring-framework/reference/data-access/transaction/declarative.html)
      (the overview and `@Transactional` sections).

## Concepts
- [ ] **IoC**: the framework creates and wires objects (beans); you declare what you need, Spring
      supplies it.
- [ ] Stereotypes: `@Component` (generic), `@Service` (business logic), `@Repository` (data access);
      `@Configuration` + `@Bean` for manual wiring.
- [ ] **Constructor injection** (preferred): dependencies are `final`, required, and easy to mock —
      connects to [[M7.05 - Testing - Writing Testable Code (Intro to TDD)]]. With a single constructor
      no `@Autowired` is needed.
- [ ] Typical layering: **Controller** (HTTP) → **Service** (logic, transactions) → **Repository**
      (persistence). Beans are singletons by default — keep them stateless.
- [ ] `@Transactional` on a service method: everything inside commits or rolls back together. By
      default it rolls back on unchecked exceptions only, and it works through a proxy — calling a
      `@Transactional` method from the same class bypasses it. Use `readOnly = true` for queries.

## Practice
**Goal:** Introduce a service layer.
**Steps:**
- [ ] Extract business logic from the controller into a `@Service`; inject it via the constructor.
- [ ] Unit-test the service with a mocked dependency ([[M7.04 - Testing - Mockito and Test Doubles]]) —
      no Spring needed.
- [ ] Add a service method that changes two things and mark it `@Transactional`; make it throw
      halfway and confirm nothing was saved (after the next topic adds a database).

## Self-check
Answer out loud or on paper first, then expand to compare.

> [!question]- What does "inversion of control" mean in Spring?
> Your classes don't create their collaborators; the container creates and injects them. Control
> over object creation and wiring moves to the framework.

> [!question]- Why is constructor injection preferred over field injection?
> Dependencies are explicit, `final`, and required; the class can be created in a plain unit test
> with mocks — no reflection or Spring context needed.

> [!question]- A `@Transactional` method throws a checked exception. Is the transaction rolled back?
> Not by default — only unchecked exceptions (and `Error`s) trigger rollback. Use `rollbackFor` or
> throw an unchecked exception.

> [!question]- Why can calling a `@Transactional` method from another method in the same class silently skip the transaction?
> Transactions are applied by a proxy around the bean; an internal `this.method()` call never goes
> through the proxy.
