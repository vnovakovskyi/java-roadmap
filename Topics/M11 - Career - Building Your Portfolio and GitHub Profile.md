# Building Your Portfolio and GitHub Profile

> [!info] Topic
> **Area:** Career · **Module:** 11 · **Priority:** must · **Est:** 4h
> **Why this matters:** For a junior without commercial experience, your GitHub *is* your
> experience. Reviewers spend a couple of minutes on it — make those minutes show working, tested,
> documented code you can explain line by line.

## Learning Objectives
- Choose and polish the projects that represent you.
- Make each repository easy to understand and run.
- Present yourself with a clean GitHub profile.

## Learn
- [ ] Read:
      [Managing your profile README](https://docs.github.com/en/account-and-profile/how-tos/profile-customization/managing-your-profile-readme)
      (GitHub Docs).
- [ ] Revisit [Make a README](https://www.makeareadme.com/) and
      [[M10 - Project - Good Habits (Logging, Config, README)]].
- [ ] Compare your skills with the [Java](https://roadmap.sh/java) and
      [Spring Boot](https://roadmap.sh/spring-boot) maps on roadmap.sh — they show what employers
      expect at a glance.

## Concepts
- [ ] 2–3 strong projects beat 20 tutorial copies: your capstone, Bookshelf, and ideally one project
      from a domain you care about.
- [ ] Each repository: a README (what, why, how to run, API examples or screenshots), tests, a green
      CI badge, a sensible commit history, a license — and no secrets in the history.
- [ ] Pin the best repositories on your profile; add a short profile README (who you are, what you
      build, how to reach you).
- [ ] A live demo is a bonus, not a requirement — free hosting offers change often; a reliable
      `docker compose up` is enough.
- [ ] Small open-source contributions (docs, tests, bug fixes) show you can work in someone else's
      codebase.
- [ ] Be ready to explain every line: interviewers pick a file and ask why it's written that way.

## Practice
**Goal:** A portfolio a reviewer understands in two minutes.
**Steps:**
- [ ] Audit each candidate repository against the checklist above and fix the gaps.
- [ ] Pin your top 2–3 repositories and write a profile README.
- [ ] Ask someone to clone one project and run it using only the README; fix whatever confused them.
- [ ] Make one small contribution to an open-source project (this roadmap counts).

## Self-check
Answer out loud or on paper first, then expand to compare.

> [!question]- What does a reviewer look at first in your repository?
> The README: what the project does, how to run it, and whether it looks maintained — then tests, CI
> status, and a couple of source files.

> [!question]- Why are a few polished projects better than many small ones?
> They show you can finish, test, document, and maintain something — the actual job. Many half-done
> tutorial copies show only that you followed instructions.

> [!question]- An interviewer opens a random class in your project. What should you be able to do?
> Explain what it does, why it's designed that way, what alternatives you considered, and how it's
> tested.

## Definition of Done
- [ ] My best 2–3 projects are polished, tested, and documented.
- [ ] My GitHub profile is pinned and has a short README.
- [ ] Someone else ran one of my projects from its README alone.
- [ ] I can answer the Self-check questions without peeking.
